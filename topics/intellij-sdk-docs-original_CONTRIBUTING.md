# Contributing to the IntelliJ Platform SDK

<link-summary>Basic rules on contributing to the IntelliJ Platform SDK documentation.</link-summary>

This document describes our contribution guidelines for the open-source IntelliJ Platform SDK documentation and sample code.
Before you begin contributing content to the SDK, please read this page thoroughly as well as the [Code of Conduct](intellij-sdk-docs-original_CODE_OF_CONDUCT.md) and [License](https://github.com/JetBrains/intellij-sdk-docs/blob/main/LICENSE.txt) documents.

For information about contributing to the IntelliJ Platform itself, please visit [](platform_contributions.md).

## Creating IntelliJ Platform SDK Content

Content contributions to the IntelliJ Platform SDK are very welcome!

Before creating content for a new topic or adding large sections to the existing pages, please create an issue in the [IJSDK YouTrack project](https://youtrack.jetbrains.com/newIssue?project=IJSDK&clearDraft=true&c=) to ensure we are not working on the same topic, and to agree on the form of the content draft.
Checking with us before starting the work will reduce the risk of creating content that is unnecessary and won't be accepted.

Please clone the _intellij-sdk-docs_ project from [GitHub](https://github.com/JetBrains/intellij-sdk-docs), make additions or changes, and submit a pull request.
Alternatively, start by clicking on the <control>Edit page</control> link on the top of each page.

Before creating or altering content, please consult these guides:

* [](sdk_style.md).
  This guide describes documentation conventions in terms of content style and syntax.
* [](sdk_code_guidelines.md).
  Conventions for code sample organization, project settings, and naming conventions are described in this document.

## Repository Structure

The documentation is built with [Writerside](https://www.jetbrains.com/writerside/).
There is no local command-line build; install the [Writerside](https://plugins.jetbrains.com/plugin/20158-writerside) plugin to preview pages and validate links, anchors, and includes in the IDE.

| Path                                | Purpose                                                                                                                                                       |
|-------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------|
| <path>topics/</path>                | All topic pages (<path>*.md</path>, plus a few <path>*.topic</path> XML pages). File names are unique across the whole tree and are referenced by name only. |
| <path>reference_guide/</path>       | [Incompatible API changes](api_changes_list.md) lists.                                                                                                       |
| <path>ijs.tree</path>               | The [table of contents](sdk_style.md#table-of-contents). Every page must be registered here.                                                                 |
| <path>v.list</path>                 | Variables like the current platform version, link prefixes such as `%\gh-ic%`, and library versions.                                                          |
| <path>labels.list</path>            | Version and status labels (`2026.1`, `Deprecated`, `Obsolete`, etc.) used by `<primary-label>`.                                                               |
| <path>topics/_shared/</path>        | Reusable snippets, for example, the `ep` and `epLink` snippets in <path>snippets.topic</path>.                                                               |
| <path>images/</path>                | Images, one subdirectory per area or page.                                                                                                                    |
| <path>code_samples/</path>          | Buildable [](code_samples.md). Paths in `{src="..."}` attributes are relative to this directory.                                                              |
| <path>.github/scripts/</path>       | Scripts generating some of the content.                                                                                                                       |

### Generated Content

The following files or regions are generated by scripts in <path>.github/scripts</path> and are overwritten automatically, so do not edit them:

* <path>topics/_generated/</path> (Android Studio releases), generated by <path>android_studio_releases.main.kts</path>.
* <path>topics/appendix/resources/ep_lists/_generated/</path> (extension point lists).
* The region between `GENERATED CONTENT START` and `GENERATED CONTENT END` in <path>plugin_configuration_file.md</path>, generated by <path>generate_descriptor_pages.main.kts</path>.
* The region between `GENERATED CONTENT START` and `GENERATED CONTENT END` in <path>v.list</path>, generated by <path>libraries_releases.main.kts</path>.

To change generated content, change the script or its upstream source instead.

## Research Before Writing

1. Search for existing coverage of the API, extension point, or concept first.
   Prefer extending an existing page or section over creating a new page.
2. Verify every API claim against the IntelliJ Platform sources.
   Class names, method signatures, extension point names, and since-versions must match the code
   at the release tag defined by `%\ijPlatformReleaseTag%` in <path>v.list</path>.
   See [](sdk_style.md#links-to-intellij-platform-source) for linking to the sources.
3. Prefer live code over pasted code.
   If a sample in <path>code_samples/</path> demonstrates the topic, [include it](sdk_style.md#source-code) with `{src="..." include-symbol="..."}` instead of copying it.

## Scope and Granularity

* A page covers one concept or feature and answers one question a plugin developer has, for example, "How do I provide inlay hints?".
* Typical pages are 50–200 lines long.
  If a page grows beyond about 400 lines, split it into child pages nested under it in <path>ijs.tree</path>.
* Add a section to an existing page when the content only makes sense in the context of this page or is shorter than about 40 lines.
  Create a new page when the content has its own extension points or API, and readers would search for it directly.
* For version-specific APIs, document the current approach first.
  Put legacy approaches in a later section titled with the version, for example, `## Pre-2025.1: ...`,
  or in tabs: `<tab title="2023.2+">` and `<tab title="Pre-2023.2">`.

### Page Types

Model new pages on the following exemplars:

| Type                                | Exemplar                    | Characteristics                                                                                                                                                       |
|-------------------------------------|-----------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Feature or extension point reference | [](inlay_hints.md)          | Introductory text, an _Implementation_ section with one subsection per API or extension point, and a list of examples linking to real implementations in the IntelliJ Platform. |
| Concept or architecture             | [](background_processes.md) | Explains a platform mechanism in sections by aspect (starting, cancellation, progress). Legacy information is in a final _Pre-XXXX.X_ section.                       |
| Tutorial step                       | [](annotator.md)            | Numbered title, `<tldr>` with _Reference_, _Code_, and _Testing_ links, shared tutorial header, and steps backed by <path>code_samples/</path>.                        |
| Template-based guide                | [](remote_procedure_calls.md) | Walks through an external template project, linking each referenced file.                                                                                          |

A new page follows this skeleton (see [](sdk_style.md#page-format) for details):

```md
<!-- Copyright 2000-2026 JetBrains s.r.o. and contributors. Use of this source code is governed by the Apache 2.0 license. -->

# Concise Page Title

<link-summary>One sentence describing what the page covers.</link-summary>

<tldr>

**Reference**: [](related_page.md)

**Code**: [`SomeClass`](%gh-ic%/platform/.../SomeClass.kt)

</tldr>

Introductory text without a heading: what the feature is and when a plugin needs it.

## Implementation

To provide X, implement [`XProvider`](%gh-ic%/platform/.../XProvider.kt)
and register it in <include from="snippets.topic" element-id="ep"><var name="ep" value="com.intellij.xProvider"/></include>.
```

## Updating Related Files

Depending on the change, update the following files too:

<path>ijs.tree</path>
: Register every new page, and configure [redirects](sdk_style.md#redirects) when renaming or moving a page.

[](content_updates.md)
: Add an entry for every notable change (new page, new section, significant rewrite) under the current year and month, reusing the month heading if it already exists.
  Write entries in the imperative ("Add", "Document", "Describe").

[](api_changes_list.md)
: Document incompatible API changes in <path>reference_guide/api_changes_list_20XX.md</path>.
  Entries must follow the patterns described in the HTML comment at the top of the file **exactly**, as they are validated by CI.
  APIs marked as deprecated for removal, experimental, internal, or scheduled for removal are not documented there.

[](api_notable.md)
: Document notable non-breaking API changes and new APIs in <path>api_notable_list_20XX.md</path>, grouped by version.

<path>labels.list</path>
: When documenting a feature for a new release that has no [version label](sdk_style.md#version-label) yet, add one following the existing entries.

## Code Samples

Create new code samples only when absolutely necessary, and keep them minimal.
Follow the [](sdk_code_guidelines.md).

Build and test a changed sample from its directory using `./gradlew buildPlugin test`.
When a sample changes, check that every `{src="..."}` and `include-symbol` reference to it in topics still resolves.

## Commit Messages

* If a change is about a single page or file, prefix the subject with its file name (no path), for example, `sdk_style.md: Clarify usages of "we", "us"`.
  This applies even when supporting files change too, like the page's images, its entry in <path>content_updates.md</path>, or <path>ijs.tree</path>.
* Otherwise, write a short summary without a prefix, for example, `Add missing code fence languages`.
* Start the change description with an imperative verb in sentence case, without a trailing period.
* Do not add pull request numbers, as GitHub appends them on merge.

## Before Submitting

Check that:

* The content is verified against the IntelliJ Platform sources at the current release tag.
* The page structure, text formatting, and voice follow the [](sdk_style.md).
* New pages are registered in <path>ijs.tree</path>, and renamed pages have redirects and updated inbound links.
* Version-specific APIs have a version label or since-version wording.
* Notable changes have an entry in <path>content_updates.md</path>.
* Changed code samples build, and their `{src="..."}` references resolve.
* Generated content is not edited.
